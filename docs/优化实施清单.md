### 🔴 三个反转结论（必须记住，否则以后会重犯）

**反转 1：JPEG 慢 424ms 的真凶不是 `optimize=True`，是「压平到白底」走了线性空间浮点路径。**

`prepare_image_for_export` → `composite_over_background` → `UnifiedAlphaCompositor.blend_normal`
对整图做 float64 线性空间混合 + 抖动。而这里只需要「透明区压到常量白底」，
用 `Image.alpha_composite` 就够：

| 方案 | 1080×1350 | 差异 |
|---|---|---|
| 线性 float64 | 418 ms | 基准 |
| `Image.alpha_composite` | **9 ms** | **快 46×** |

像素差异：平均 0.01/255，最大 7/255，仅 0.10% 像素差 >2（全在半透明边缘）。

至于 `optimize=True`：实测 q=95 时 19.6ms→3.2ms，但体积 45KB→65KB（**大 44%**）。
是「3–6 倍速度换 44–57% 体积」，属于质量取舍，不是纯粹的浪费。已做成 `BTPW_JPEG_OPTIMIZE` 开关，默认保留优化。

**反转 2：libvips 在纯编码环节**比 PIL 慢**，不是快。**

| 场景 | vips | PIL |
|---|---|---|
| PNG 1080×1350 | 15 ms | **11 ms** |
| PNG 4000×5000 | 148 ms | **102 ms** |

原因：PIL 图像交给 vips 必须整图拷贝一次（PIL→bytes→vips），这次拷贝的代价
大于 vips 编码省下的部分。vips 的优势在「合成与写盘一体化、中间结果不物化」的流式管线，
而我们架构是「先合成为 PIL Image 再编码」，必然物化，用不上。

**并且发现一处隐患**：原 `_should_try_vips` 的逻辑是「装了 pyvips 就自动走 vips」，
等于**用户装了 pyvips 会让导出变慢**。已改为默认关闭，用
`BTPW_ENABLE_VIPS_ENCODE=1` 或 `job.backend="vips"` 显式启用。

> vips 在流式场景确实快：图层预解码后「合成+写盘」175ms vs Pillow 900ms（快 5×）。
> 但要重写整条合成链，属于 P2 之后的独立工程，不在本次范围。

**反转 3：`IntelligentRenderCache` 不是死代码，我之前的「零命中」是测错了。**

之前的基准一直传 `force_refresh=True`，直接绕过缓存，然后我据此判断「有缓存但零命中」。
按真实调用方式（`force_refresh=False`）实测：5 次全部命中，`hit_rate=100%`。

**教训**：判断一个缓存是否失效，必须用**生产路径的调用参数**去测，
不能拿基准脚本的参数当结论。

**P0-4 为什么不做的量化依据**：

| 操作 | 4000×5000 耗时 |
|---|---|
| `Image.new`（现状） | 16.5 ms |
| `paste` 清零（复用方案） | 7.8 ms |

只省 8.7 ms —— 因为清零同样要写满 76MB，只能省一半。而当时单帧已降到 20ms，
收益 40% 但要承担「画布被外部持有后复用会污染画面」的风险，性价比不成立。
**如果将来单帧压到 10ms 以下，这项的占比会重新变得可观，到时再评估。**

## ⚠️ 先修正上一版报告的两处错误

写具体改法时发现两处结论不准确，必须先纠正，否则后面的优先级会排错。

### 修正 1：批量导出**不是**单核运行

报告里写的「`max_workers=1` 强制单核」是误读。实测：

```
cpu_count: 28
doc_seed available: True          ← 线程文档快照可正常生成
max_workers(最终): 5
```

`optimized_batch_executor.py:910` 那个降级分支只在 `_worker_document_seed is None` 时触发；
实际 `DocumentSerializer.serialize_document_data()` 成功，所以**根本没降级**。
并发数真实取值是 `min(核数-1, 核数×0.60)` = `min(27, 16)`，再被各档位规则压到 5。

**并发是真的在跑，上限偏保守。** 修正后的判断：这里值得动，但预期收益是「+30~60%」不是「×4~6」。

### 修正 2：多线程加速比是 1.72×，不是 6.22×

报告引用的 6.22× 是**纯 PIL resize** 的数字。真实管线带 35% Python 层（受 GIL 串行），实测：

| 方式 | 24 张耗时 | 吞吐 | 加速比 |
|---|---|---|---|
| 串行 | 5.51 s | 4.36 张/秒 | 1.00× |
| 4 线程（各自独立 Document） | 3.19 s | 7.52 张/秒 | **1.72×** |

**结论方向不变（并行有效），但量级要降。** 这也说明「去 Python 层」确实能换来更多并行度 —— 但那是 libvips 的事，不是换语言的事。

### P0-2 交互预览引入脏矩形（大画布的决定性改动）

**✅ 已实施**（`app/utils/fast_renderer_preview.py`）
实测：4000×5000 拖动帧 **263 ms → 19.9 ms（50.3 fps）**。

**位置**：`app/utils/fast_renderer_preview.py:390`（画布创建）、`:423`（图层循环）、`:496`（`_fast_composite` 调用）

**问题**：拖动一个图层时，`_fast_render` 会把**全部可见图层**从零重合成一遍。而拖动只影响被拖图层的新旧两个矩形。

#### 🔴 一个必须知道的限制：脏矩形**做不到**逐字节相同

原因在 `_high_quality_alpha_composite` 收尾的 `_float_to_uint8_with_dithering`：
抖动用「固定种子 + **按数组 shape** 生成随机序列」。脏区把数组切小了，
随机序列随之改变 → 抖动图案错位 → 结果差 **±1/255**。

实测验证：
```
同尺寸同内容     → 完全可重复
不同尺寸取同区域 → 1022 个像素不同（16×16 样本）
```

**所以验收标准是「最大通道差 ≤ 1」，不是「逐字节相同」。**
这个容差不是放松要求：脏区真算错时差异是**几十到上百**（实测注入「脏区减半」→ 差异 190）。
两者能清楚区分开。

**要不要为此去掉抖动？** 不建议。抖动是为了消除渐变区域的色带，
去掉会让大画布渐变背景出现肉眼可见的阶梯。±1/255 在拖动帧上完全不可见，
而且松手后 final 帧会全量重算，误差不会留在成图上。

#### 实现要点（`_dirty_region_for_layer` + `_compose_in_dirty_region`）

| 要点 | 为什么 |
|---|---|
| 脏区取**新旧位置并集** | 只算新位置，旧位置会露下层 → 残影 |
| 脏区含**效果外扩** | 描边/阴影/外发光会画到 bbox 之外，外扩不够就留边 |
| 仅 `blend_mode == 'normal'` 启用 | overlay/soft-light 依赖上下文，局部裁切会改变结果 |
| **base 必须是「去掉活动层」的底图** | 这样才能直接在 base 上叠加活动层；否则活动层下方被遮住的图层无法正确露出 |
| 失败一律 `return None` 回退全量 | 宁可慢一帧，不能出错误画面 |

**测试必须注意的两个坑**（都踩过，写在这里防止后人重犯）：

1. **必须用有真实图像的图层**。空图层 `get_layer_surface_cached` 返回 `None`，
   会被 `continue` 掉，脏矩形路径**根本走不到**，测试假绿。
2. **基准帧必须用另一份文档**。对同一文档调 `render_preview(force_refresh=True)`
   会作废交互底图缓存，使下一帧 dirty 变成整层矩形，把并集 bug 藏起来。

为此专门加了 `test_incremental_drag_takes_dirty_rect_path` —— 用 spy 断言
「脏矩形方法真的被调用过且脏区真的小于画布」。没有这条，前一条测试可能是假的。

**失败注入验证结果**（证明测试有效）：

| 注入的退化 | 测试表现 |
|---|---|
| 脏区算小一半 | ✅ 抓到：差异 190 > 1 |
| 效果外扩归零 | ✅ 抓到：`outset 0 < 22` |
| 脏矩形方法不执行 | ✅ 抓到：`calls 0 >= 1` 失败 |
| 不取新旧并集（`prev=None`）| ⚠️ **抓不到** —— 见下文说明 |

> 「不取新旧并集」抓不到，是因为当前实现每帧都从 **base** 重新裁脏区合成，
> 不累积上一帧结果，旧位置的清除天然由 base 保证。这条并集逻辑是给未来
> 「累积式脏矩形」预留的防御，在当前设计下不影响正确性。
> **如果以后改成累积式（在上一帧结果上增量绘制），必须把这条测试补强。**

**实测天花板**（4000×5000，8 层）

|---|---|---|
| 全画布重建 | 709 ms | 1.4 |
| **脏矩形只重合成被操作层** | **24.7 ms** | **40.5** |
| 收益 | **-96.5%** | — |

**改前**（`fast_renderer_preview.py:496` 附近，伪代码化但结构一致）

```python
composition = Image.new('RGBA', (render_width, render_height), (0, 0, 0, 0))
for layer in visible_layers:

```

**改后**（新增一层「帧间复用」判据，不改图层循环本身）

```python
# 1) 先判断能否复用上一帧
prev = self._last_preview_frame          # 新增：上一帧的 (image, key)
can_reuse = (
    prev is not None
    and prev.key == self._frame_key_excluding(active_layer_index)  # 除活动层外全部不变
    and self._blend_mode_allows_dirty(layer)                       # 仅 normal 走脏矩形
)

if not can_reuse:
    # 走原路径，但**保留**结果供下一帧复用
    composition = Image.new('RGBA', (render_width, render_height), (0, 0, 0, 0))
    for layer in visible_layers:
        ...
    self._last_preview_frame = (composition, self._frame_key_excluding(-1))
    return composition

# 2) 复用路径：只重合成「上一帧活动层脏区 ∪ 本帧活动层脏区」
composition = prev.image.copy()          # 只在脏矩形路径 copy 一次，不是每层一次
dirty = self._union_dirty_rect(last_rect, current_rect, expand_by=effects_outset(layer))
self._rebuild_region(composition, dirty, layers_covering=dirty 覆盖到的图层)
self._last_preview_frame = (composition, self._frame_key_excluding(active_layer_index))
return composition
```

> 注意：脏矩形路径里**必须**从「底图 + 所有覆盖该区域的图层」重合成，不能只贴活动层 ——
> 因为活动层下方的图层在移动后可能露出来。

**关键实现约束（不做就会出残影）**

| 约束 | 说明 |
|---|---|
| 脏区必须含**效果外扩** | 描边宽度、阴影偏移+模糊半径、圆角、`glow` 都要算进 `effects_outset()`。漏了就是边缘拖影 |
| 脏区取**新旧两帧并集** | 只算新位置，旧位置会留下残影 |
| 混合模式白名单 | `normal` 走脏矩形；`overlay`/`soft-light`/`multiply` 等依赖上下文，**强制走全量** |
| 尺寸匹配图层 | `_build_size_match_overrides` 参与合成时，几何变化会影响其他图层的位置，这种情况直接判定 `can_reuse=False` |
| 文字编辑覆盖层 | `omit_active_layer=True` 时脏矩形语义不同，先白名单排除 |

**风险（这是 P0 里风险最高的一项，建议单独一个 PR）**

| 风险 | 表现 | 缓解 |
|---|---|---|
| 残影 / 漏画 | 拖动后旧位置留下图层碎片 | 像素级回归：脏矩形结果 vs 全量结果必须**逐像素相等**，容差 0 |
| 混合模式结果错 | 局部裁切改变了混合上下文 | 只对 `normal` 启用，其余全量 |
| 撤销/切换文档后复用脏帧 | 画面串味 | `_last_preview_frame` 必须挂 document id + revision，任何 `_invalidate_*` 都清掉 |
| QML 侧回调时序 | 复用了旧帧但发起新的 previewChanged | 复用帧也要 bump `_preview_revision` |

### P0-3 给剩余缓存补字节预算（内存 1.3 GB → 300 MB 量级）

**位置**：`app/utils/fast_renderer_surface.py` 三处写入点 + `app/utils/fast_renderer.py:265-310` 声明

**问题定位**：`fast_renderer.py` 声明了 13 个 `OrderedDict` 缓存，**只有 2 个**（`_layer_surface_cache`、`_export_layer_surface_cache`）接了 `_set_cache_value_unlocked` 的字节预算，其余 11 个是裸的「条数上限 + popitem」。

实测代价：4000×5000 / 12 层，20 次预览 RSS **72 MB → 1087 MB**；30 次导出后 **1327 MB**。

### P0-4 持久画布，不每帧 `Image.new`

**位置**：`app/utils/fast_renderer_preview.py:390`、`app/models/document_render.py:789`

**问题**：每帧 `Image.new('RGBA', (W,H), (0,0,0,0))` 在 4000×5000 是 76 MB 的 `memset`。

**改前**

```python

```

**改后**

```python

```

```python
def _acquire_canvas(self, w: int, h: int) -> Image.Image:
    """复用画布：同一尺寸的旧画布就地清零，避免每帧 76MB memset。

    只在「上一帧画布没有被返回给调用方持有」时复用 —— 复用前必须确认
    上一帧的 composition 已不再被引用（预览 provider 里存的是转好的 QImage）。
    """
    cached = self._canvas_pool.get((w, h))
    if cached is None:
        canvas = Image.new('RGBA', (w, h), (0, 0, 0, 0))
        self._canvas_pool[(w, h)] = canvas      # 池上限 2 块，超出就丢
        return canvas
    cached.paste((0, 0, 0, 0), (0, 0, w, h))     # 就地清零
    return cached
```

**实测**：`Image.new` 4000×5000 约 **10 ms**（`PIL._imaging.fill`），`paste` 清零约 **4 ms**。

**收益 ≈ 6 ms/帧**，在 4000×5000 场景下相当于 263 ms 的 2.3%。**优先级低于 P0-1/P0-2，但成本极低。**

**风险**

| 风险 | 说明 |
|---|---|
| **画布被外部持有 → 复用后画面被改写** | 最危险。必须先确认 `composition` 返回后，调用方是否还持有引用（QML 预览 provider 存 QImage，是拷贝；但 `get_layer_surface_for_overlay` 可能持有 PIL 对象）|
| 多线程同时取画布 | 池必须加锁，或改成 thread-local |

**建议**：这一项**等 P0-2 落地后再做**。脏矩形方案本身就要引入「持久帧」，两项合并实施比分开做更安全。

## P1 · 次优先（3–4 周，换基座）

### P1-1 引入 libvips 做合成后端

**⚠️ 已部分实施，结论与预期相反 —— 纯编码环节不该用 vips。**

**位置**：`app/utils/vips_export_engine.py`

#### 实测推翻的两个假设

**假设 1（错）：vips 编码更快。** 实测（本机，pyvips 3.2.0 + libvips 8.18）：

| 场景 | vips | PIL | 结论 |
|---|---|---|---|
| PNG 1080×1350 | 15 ms | **11 ms** | vips 慢 36% |
| PNG 4000×5000 | 148 ms | **102 ms** | vips 慢 45% |

原因：PIL Image 交给 vips 必须**整图拷贝一次**（`PIL → np.array → bytes → new_from_memory`），
这次拷贝（4000×5000 实测 55–88ms）大于 vips 编码省下的部分。

尝试用 `memoryview` 省掉拷贝（58ms vs 88ms），但 `new_from_memory` 不接管 buffer 所有权，
**4000×5000 上稳定段错误（exit 139）**，即使把 bytes 存局部变量 + `copy_memory()` 也不行。
为 30ms 冒崩进程的风险不值得，已回退。

**假设 2（对，但代价高）：vips 在流式合成时确实快。**

| 方案 | 4000×5000 / 8 层「合成+写盘」 |
|---|---|
| vips（图层已预解码） | **175 ms** |
| Pillow（现状） | 663 ms 合成 + 238 ms 写盘 = **900 ms** |

快 5×。但前提是图层以 vips 形式持有、且中间结果不物化 ——
这要求**重写整条合成链**（surface 准备、混合模式、文字层全部要迁），
而这条链刚在本次优化里降到 20ms/帧（拖动场景）。属于独立的大工程，不在本次范围。

#### 本次实际改动

1. **修正一个隐患**：原 `_should_try_vips` 的逻辑是「装了 pyvips 就自动走 vips」。
   按实测，这等于**用户装了 pyvips 反而让导出变慢 35–45%**。
   已改为默认关闭，用 `BTPW_ENABLE_VIPS_ENCODE=1` 或 `job.backend="vips"` 显式启用。
2. 修正 `requirements.txt` 里「pyvips 加速大图编码」这条误导性注释。
3. 保留 `save_image` 全部代码 —— 将来走 vips 流式合成时，编码段可直接复用。

#### 如果将来要做完整 vips 迁移，收益预期

| 层 | 保留 | 理由 |
|---|---|---|
| 文字渲染 | **Pillow** | vips 的文字排版能力弱，中文字距/竖排/描边做不了 |
| 图层 surface 准备 | **Pillow** | 缩放到目标尺寸、特效预渲染 |
| **合成（多 surface 叠加）** | **vips** | `composite2` + demand-driven 流水线，内存按条带流动 |
| 编码 | **vips** | 与合成在同一流水线里，不物化 —— 这是唯一能赢的场景 |

**风险（届时适用）**

| 风险 | 缓解 |
|---|---|
| 打包体积 + DLL 依赖（glib 一串） | `pip install pyvips-binary` 自带运行时；onedir 安装版 |
| 色彩管理差异（vips 默认带 ICC） | 显式关 ICC，与现有输出对齐后再开 |
| PIL↔vips 内存交接段错误 | **不要用 `new_from_memory` + 临时 buffer**，一律走 numpy 路径 |
| 混合模式语义差异 | vips 的 `over` 是 sRGB 空间的 Porter-Duff，与现有 `blend_photoshop_srgb` 需逐一对齐后测像素 |
| 降级路径平时不跑 → 坏了不知道 | 加 `BTPW_FORCE_PIL_RENDER=1`，CI 里跑一遍全量测试 |

**验收**：批量吞吐 ≥ 25 张/秒（8 层 1080×1350 PNG，当前 4.36 张/秒）；4000×5000 8 层单帧 < 60 ms（当前 411 ms）。

### P1-2 导出 JPEG 编码链路

**✅ 已实施。但真凶不是 `optimize=True`，是「压平到白底」走了线性空间浮点路径。**

#### 真实定位过程

先按原计划查 `optimize`，实测发现它只是次要因素：

| 设置 | 耗时 | 体积 |
|---|---|---|
| `optimize=True` q=95 | 19.6 ms | 45 KB |
| `optimize=False` q=95 | 3.2 ms | 65 KB |
| `optimize=True` q=90 | 6.2 ms | 37 KB |
| `optimize=False` q=90 | 3.6 ms | 58 KB |

`optimize=True` 是「3–6 倍时间换 30–44% 体积」，是**质量取舍，不是浪费**。
而 464 ms 的耗时根本不在编码 —— 继续拆：

```
prepare_image_for_export:  717 ms   ← 真凶
_encode_jpeg_to_bytes:       7 ms
```

717 ms 全花在 `composite_over_background` → `UnifiedAlphaCompositor.blend_normal`：
它把整图转 float64、转线性色彩空间、混合、再转回来、再加抖动。
但这里的需求只是「透明区压到常量白底」，是不透明底上的标准 Source-Over，
退化成一次普通 alpha 混合，Pillow 的 C 实现就够。

#### 改法（`app/services/render_quality.py:53`）

**改前**

```python
bg_rgba = Image.new("RGBA", image.size, tuple(background) + (255,))
return UnifiedAlphaCompositor.blend_normal(bg_rgba, image, 1.0).convert("RGB")
```

**改后**

```python
# 底是不透明常量色，Source-Over 退化为普通 alpha 混合，用 Pillow C 实现即可。
# 需要严格复现旧的线性空间结果时设 BTPW_LINEAR_FLATTEN=1。
bg_rgba = Image.new("RGBA", image.size, tuple(background) + (255,))
return Image.alpha_composite(bg_rgba, image).convert("RGB")
```

#### 实测结果

| 方案 | 1080×1350 | 差异 |
|---|---|---|
| 线性 float64（改前） | 418 ms | 基准 |
| `Image.alpha_composite`（改后） | **9 ms** | **快 46×** |

像素差异：平均 0.01/255、最大 7/255、仅 0.10% 像素差 >2（全在半透明边缘）。

**端到端 JPEG 导出：424 ms → 49 ms（快 8.7×），体积不变。**

#### `optimize` 的处理

不是无条件关掉，而是做成开关：

```python

# BTPW_JPEG_OPTIMIZE=0 时关闭，换 3–6 倍编码速度，代价是体积大 44–57%
```

默认保留 `True`：导出是低频操作，体积对用户更直观。

| 导出并发上限 | ✅ | 28 核 5 → 7 线程 |
| 缓存预算低配自适应 | ✅ | RAM×10% 上限 |

**缓存预算最终覆盖情况**（这是「内存」这一项是否真做完的判据）：

| 有字节预算（9 个，存位图） | 只有条数上限（5 个，只存元数据） |

| `_layer_surface_cache` | `_layer_positions_cache`（位置列表） |

| `_interactive_scaled_cache` | `_visible_layers_session_cache`（指纹+引用） |
| `_size_override_surface_cache` | |
| `_size_match_auto_mask_cache`（**本次补上**）| |
| `_batch_raw_image_cache` | |

> 最后补的 `_size_match_auto_mask_cache` 是审计时发现的真漏洞：它存的是**完整 PIL 图像**，
> 96 条无预算时 2000×2500 素材最坏 **1831 MB**、4000×5000 最坏 **7324 MB**。
> 其余 5 个只存坐标/引用/指纹，单个条目是 KB 级，条数上限已足够。

### 一句话总结

**「卡顿」这个用户能感知的核心问题解决了**（大画布从 3.8fps 到 33fps，导出快 8.7 倍，
内存不再涨）。**但「启动慢 1 秒、导出等 1.5 秒、QML 单文件 9300 行」这三件事一个都没动**
—— 它们不属于「卡顿」，属于「体验粗糙」，需要单独排期。

如果目标是「用户不再抱怨卡」，现在可以封板交付。
如果目标是「整体工程品质」，上面 8 项还没做完。

## 四项决策的建议与依据（2026-11-03 已查证）

### 决策 1：`.cmp` 兼容版本数 → **建议：不做 P2-2，没有「几个版本」这回事**

**查证结果（推翻了我的原假设）**：

| 事实 | 证据 |
|---|---|
| `.cmp` 就是 **pickle 后的纯 dict**，没有自定义类 | `document_serializer.py:133` 写出 9 个顶层字段：`version / canvas_width / canvas_height / layers / selected_layer_index / export_settings / view_settings / layer_size_matches / binding_groups` |
| 当前格式版本 **5** | `document_export_serialize.py:130` |
| **`doc_version` 读出来只用于打印日志，没有任何按版本的分支** | `document_export_serialize.py:174` 之后的加载逻辑里，`doc_version` 再没被引用过 |
| 兼容靠「字段缺省填充」而非版本分支 | `document_export_serialize.py:174` 起大量 `document_data.get('xxx', 默认值)`；图层侧靠 `serialization_compat.normalize_layer_data` 把旧字段 `layer_type` 映射成 `type` |

**所以「有几个版本要兼容」这个问题的前提就不成立** —— 代码从来不是按版本号兼容的，
而是「能读到就带上，读不到用默认值」。`serialization_compat.py` 里也没有 version 相关代码。

**建议**：
- **不要因为「格式兼容」这个理由去卡 P2-2**，它不是障碍。
- 但 P2-2（预览/导出合成路径合一）仍然**不建议现在做**，理由换成了更实际的两条：
  1. 本次刚把两条路径各自的性能问题解决掉（预览走脏矩形、导出走 `alpha_composite`），
     合一后状态好的性能未必能保住；
  2. 合一必然改变输出，需要「黄金图」回归集（20 文档 × 3 格式 × 逐像素），
     这套基建目前没有，得先建。
- **如果以后要做**：不需要「兼容几个版本」，只需要**先用现有代码生成一批
  `.cmp` 样本作为回归输入**（版本 5 的、以及手工删字段模拟的 v1/v3），
  改完后确认这些文件都能正常打开、渲染结果在容差内。

---

### 决策 2：JPEG 体积 vs 速度 → **建议：保持现状（`optimize=True`）**

**关键新证据：`optimize` 只影响熵编码，解码后像素完全一致。**

实测（1080×1350 渐变图，q=95）：
```
optimize=True : 29.4 ms / 61 KB
optimize=False:  4.1 ms / 83 KB
解码后逐像素比较：完全相同（np.array_equal = True）
```

也就是说 **关掉 optimize 不省画质、也不损画质，纯粹是「用 CPU 换文件体积」**。

**代价换算**（同一张图）：

| 方案 | 耗时 | 体积 |
|---|---|---|
| `optimize=True` q=95 | 29.4 ms | 61 KB |
| `optimize=False` q=95 | 4.1 ms | 83 KB |
| `optimize=False` q=81（想压到 61KB）| ~3 ms | 60 KB |

**建议保持 `optimize=True`**，理由：
1. 批量导出的瓶颈**不在编码**。本次实测：2000×2500 + 299KB 上限的完整导出是 52 ms，
   其中编码只占十几毫秒；真正的成本在渲染（本次已从 615ms 降到 20ms 量级）。
   关掉 optimize 能把导出从 52ms 压到 29ms，但相对整体链路收益有限。
2. **体积对用户更直观**。导出的是电商图，要上传平台、有体积限制，
   44% 的体积差会直接影响可用性。
3. 默认导出设置是 `max_file_size_kb=299` + `dynamic_budget_enabled`，
   体积越小，二分搜索越容易一次命中，反而更快。

**什么条件下我会改口**：如果实测发现某类用户「导出几千张、不在乎体积」，
再让他在界面里选「速度优先」档，走 `BTPW_JPEG_OPTIMIZE=0`。
**现在不需要动默认值。**

---

### 决策 3：导出占 75% CPU → **建议：保持 0.75，但要加一个「导出时不渲染预览」的联动**

**现状**：`BTPW_BATCH_CPU_CAP` 默认 0.75。28 核机器实际给 7 个线程。

**保持 0.75 的理由**：导出是用户主动发起的批处理，
用户的心理预期是「点了就快点跑完」，不像拖拽那样必须留出交互余量。

**但有一个真问题需要补**：导出期间如果用户继续拖画布，
预览渲染会和 7 个导出线程抢 CPU，两边都变慢。现在的缓解办法是
`_is_export_preview_frozen` 复用最后一帧快照，但那只在缓存命中时生效。

**建议（不改默认值，改联动）**：
- 导出进行中，把预览的 `interactive_low_quality` 强制置为 `True`（已有参数，只需在
  `workspace_vm_preview` 里加一个判据）；
- 若用户没在交互，干脆暂停预览定时器。
这样既保住导出速度，又不会让界面卡死。

**风险**：这是行为改动，需要验证「导出中拖动画布」的实际体感。
**建议单独一个小 PR，不要和性能改动混在一起。**

---

### 决策 4：低配机器 → **建议：缓存预算按物理内存自适应（已在本次实施）**

**查证结果**：缓存预算合计 **1568 MB 是固定值**，不随物理内存缩放：

| 机器内存 | 预算占比 |
|---|---|
| 4 GB | **38.3%** ← 危险 |
| 8 GB | 19.1% ← 偏高 |
| 16 GB | 9.6% ← 正常 |
| 32 GB | 4.8% |

4GB 机器上 1.5GB 缓存 + 导出并发（单任务 4000×5000 估算 198MB）会直接触发换页。

导出并发的**内存守卫本身是自适应的**（`_calculate_memory_guard_in_flight_limit`
按 `psutil` 可用内存算），但**缓存预算是死的**。

**已在本次实施**（`fast_renderer_cache.py:_resolve_cache_budget_bytes`）：
- 未显式设环境变量时，预算再加一层「物理内存 × 10%」上限；
- 显式设了环境变量则以环境变量为准（便于压测和用户调优）。

实测收敛结果：

| 机器内存 | 单项 192MB 预算 |
|---|---|
| 4 GB | 收敛到 ≤410MB 总上限内 |
| 8 GB | 收敛到 ≤819MB |
| 16 GB 及以上 | 不变（保持原值） |

**验证**：`check_architecture.py` 4 项通过，71 项渲染/导出测试全过。

## 新增的环境变量开关一览

> 所有 `*_MB` 缓存预算在**未显式设置**时，都会再受「物理内存 × 10%」上限约束
> （4GB 机器上会自动收敛，16GB 及以上保持原值）。显式设置则完全以环境变量为准。

| 变量 | 默认 | 作用 |
|---|---|---|
| `BTPW_LAYER_CACHE_MB` | 512 | 图层 surface 缓存字节上限 |
| `BTPW_INTERACTIVE_BASE_MB` | 192 | 交互底图缓存上限（**新增**）|
| `BTPW_INTERACTIVE_LAYER_MB` | 128 | 交互活动层 surface 上限（**新增**）|
| `BTPW_INTERACTIVE_SCALED_MB` | 160 | 交互降采样结果缓存上限（**新增**）|
| `BTPW_SIZE_OVERRIDE_MB` | 192 | 尺寸匹配结果缓存上限（**新增**）|
| `BTPW_AUTO_MASK_MB` | 192 | 自动遮罩结果缓存上限（**新增**，存的是完整图，最坏曾达 1.8GB）|
| `BTPW_BATCH_CPU_CAP` | 0.75 | 导出并发 CPU 占用上限（**新增**）|
| `BTPW_JPEG_OPTIMIZE` | 1 | JPEG Huffman 优化（**新增**，0=快但体积大 44%，画质不变）|
| `BTPW_LINEAR_FLATTEN` | 0 | JPEG 压平走旧的线性空间路径（**新增**，用于像素级对齐）|
| `BTPW_ENABLE_VIPS_ENCODE` | 0 | 启用 vips 编码（**新增**，实测更慢，慎用）|
| `BTPW_DISABLE_VIPS` | 0 | 禁用 vips（原有）|
