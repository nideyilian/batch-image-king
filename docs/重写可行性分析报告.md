# 批图王 性能瓶颈分析与跨语言重写可行性评估

> 实测时间：2026-11-03 · 版本 1.3.0 · 平台 Win32 / Python 3.12.10 / PySide6 6.11.1 / Pillow 12.3.0
> 方法：真实代码调用计时（非估算）+ cProfile 热点定位 + 对照实验（同算法纯 PIL 实现、理想架构上限）+ 市面成熟实现横向取证
> 所有数字均为本机实测中位数；标注「引用」的为公开基准，非本机数据。
>
> **⚠️ 本文档有两处结论已在后续核对中修正，以 `docs/优化实施清单.md` 开头「先修正」一节为准：**
> 1. 批量导出**不是**单核运行 —— 实测 `max_workers=5`（28 核机器），线程文档快照正常生成，
>    `optimized_batch_executor.py:910` 的降级分支未触发。
> 2. 真实管线多线程加速比是 **1.72×**（24 张，串行 5.51s → 4 线程 3.19s），
>    不是文中引用的 6.22× —— 后者是纯 PIL resize 的数字，不含 35% Python 层。

## 一、结论先行

**不建议用 Java 或任何语言重写。这是一个算法与内存管理问题，不是语言问题。**

三条硬证据：

1. **65% 的耗时发生在 Pillow 的 C 层，不是 Python 解释器。**
   8 层 1080×1350 交互帧实测 31.0 ms，同样逻辑的纯 PIL 手写版本 20.1 ms。
   Python 业务层（属性访问、缓存键计算、信号、锁）只占 35%。把这些全部搬到 Java，
   乐观估计也就省掉这 35% —— 而 Java 的 `Graphics2D` 做同样的事并不比 Pillow 快（引用：单张缩放 22 ms vs libvips 4.4 ms）。

2. **真正的地板是「每合成一层就 copy 一次全画布」。**
   `unified_alpha_compositor.py:490` 的 `result = background.copy()` 在 8 层时执行 8 次
   （`fast_renderer_composite.py:544` 有一个同源副本，但只有 `low_quality_preview` 分支会走到）。
   4000×5000 画布单帧 76 MB，8 次拷贝 = 608 MB 内存流量。
   去掉这行 copy → 实测 398 ms 降到 240 ms（**-40%**）；
   再叠脏矩形只重合成被拖动的那层 → **24.7 ms，40.5 fps（-90%）**。
   这个改动与用什么语言无关，Java 同样会踩。

3. **换语言的收益天花板被 libvips 直接盖过去了。**
   同一段合成逻辑，libvips 比 Pillow 快 2.7×、内存只占 1/11（引用 libvips 官方基准：pillow-simd 1.51 s / 1040 MB vs vips-c 0.55 s / 94 MB）。
   接入 libvips 是**换掉一个库**，重写是**换掉 68,575 行代码 + 1,180 项测试 + 所有用户 .cmp 文件**。前者 2–4 周，后者 6–12 个月且必然功能回退。

**推荐路径**：留在 Python + QML，动渲染内核（脏矩形 + libvips + 缓存字节预算）。分三阶段，第一阶段 1–2 周即可拿掉 60% 以上的卡顿感。

**什么条件下我改口**：见第八节「改口条件」，共 3 条明确触发线。

### 2.5 导出吞吐

| 场景 | 耗时 | 吞吐 |
|---|---|---|

| 导出级渲染 8 层（1080×1350，热态） | 26 ms | — |
| 导出级渲染 8 层（2000×2500） | 143 ms | — |

> 注：批量导出走独立进程（阈值 200 张）。**已修正**：进程内并发实测为 `max_workers=5`（28 核机器），
> 不是单核 —— `optimized_batch_executor.py:910` 的降级分支只在文档快照生成失败时触发，实测未触发。
> 上限取自 `min(核数-1, 核数×0.60)` 再经档位规则收敛，偏保守。

### 2.6 内存 — 最严重的一项

4000×5000 画布、12 图层、连续 20 次预览：

| 时点 | RSS |
|---|---|
| 基线 | 69 MB |
| 建 12 层后 | 72 MB |
| **20 次预览后** | **1,087 MB** |
| 再 30 次导出渲染后 | **1,327 MB** |

涨了 **1.25 GB**，而缓存系统自报「内存占用 5.5 MB」。

根因已定位：`fast_renderer.py:243` 起的多级缓存里，**只有 `_layer_surface_cache` 和 `_export_layer_surface_cache` 有字节预算**（512 MB / 384 MB），其余 **11 个 OrderedDict 只有条数上限、没有字节预算**：

- `_interactive_base_cache`：上限 16 条，**无字节预算** → 4000×5000 单帧 76 MB × 16 = **1.2 GB**
- `_interactive_layer_surface_cache`：64 条，无字节预算
- `_size_override_surface_cache`：192 条，无字节预算
- `_batch_processed_entries`：512 条，无字节预算

代码注释里已经写明「条数上限管不住内存：96 个 2000×2000 图层就是 1.5 GB」，但这条教训只修了 2 个缓存，剩下 11 个没跟上。

## 三、瓶颈定位：四层归因

按「改一处能收回多少」排序，不按发现顺序。

### P0 · 算法层（改动最小、收益最大）

#### P0-1 每层一次全画布拷贝

- 位置：`app/utils/unified_alpha_compositor.py:490`（默认路径）／`app/utils/fast_renderer_composite.py:544`（低质量分支）
- 代码：`result = background.copy(); result.paste(fg_crop, ...)`
- cProfile 实测（8 层 10 帧）：`Image.copy()` **158 ms / 372 ms = 42%**，`paste` 91 ms = 24%，合计 **66%**
- 对照实验（4000×5000，8 层）：

| 方案 | 耗时 | 相对 |
|---|---|---|
| A 现行：每层 copy 全画布 + paste | 258 ms | 基准 |
| B 局部区域合成（只处理前景矩形） | 162 ms | **-37%** |
| **B′ 只去掉 `background.copy()`（一行改动，已实测于 `composite_layer`）** | **240 ms** | **-40%** |
| C numpy 单 buffer 手工混合 | 3,234 ms | +1154%（更慢，PIL 的 C 循环已经很快） |
| **D 理想：脏矩形只重合成被操作层** | **24.7 ms** | **-90%，40.5 fps** |

结论很明确：**不要用 numpy 重写合成**（实测慢 12 倍），要害是「不要整画布拷贝」和「不要整画布重合成」。

#### P0-2 交互预览没有脏矩形

现在拖一个图层，`render_preview` 会把全部图层重新合成一遍。而拖动只会影响被拖图层的新旧两个矩形区域。这是 P0-1 在上层的放大。

#### P0-3 全画布透明底图每帧重建

`document_render.py:789` 与 `fast_renderer` 里每帧 `Image.new('RGBA', (W,H), (0,0,0,0))`，4000×5000 是 76 MB 的 `memset`。可复用持久画布。

### P1 · 内存管理层

#### P1-1 11 个缓存无字节预算（见 2.6）

这是长时运行崩溃/OOM 的直接原因。修复成本极低（照抄 `_layer_surface_cache` 已有的字节计数 + `close()` 逻辑），收益是**内存从 1.3 GB 压回 300 MB 量级**。

#### P1-2 `IntelligentRenderCache` 实际未生效

`get_intelligent_cache()` 的统计：`total_entries=1, hit_count=0, miss_count=0, hit_rate=0` —— 20 次预览只进去 1 条，命中 0 次。这个 684 行的「智能缓存」在预览热路径上基本是死代码，却仍在 `document_render.py:946` 被查询。属于「看起来有优化、实际没有」的账。

### P2 · 并发与调度层

#### P2-1 批量导出渲染不并行

- `optimized_batch_executor.py:910`：`if self.is_batch_mode and not self._worker_document_seed and self.max_workers > 1: self.max_workers = 1`
- 结果：8 核机器跑批量导出，**只用一个核**
- 实测佐证：Pillow 的 `resize` / `composite` 会释放 GIL，8 线程做同样 resize 有 **6.22× 加速**（168 ms → 27 ms）。
  **但真实管线达不到这个数** —— 带 35% Python 层后，4 线程导出实测只有 **1.72×**（24 张：5.51 s → 3.19 s）。
  所以并行化有效，但要按 1.7× 而不是 6× 做预期。

#### P2-2 预览全程串行锁

`_serialized_preview` 装饰器（`fast_renderer_preview.py:48`）给 4 个预览入口都加了同一把 `_preview_render_lock`。UI 线程的同步兜底（`workspace_vm_preview.py:270 _render_preview_sync`）与后台 `QThreadPool` 任务抢同一把锁 → 一次慢渲染会连带卡住 UI 线程。

#### P2-3 导出子进程启动税

每次批量导出起一个新进程，付 **1,476 ms** 的 import 成本，且进程内仍是单线程渲染。等于「付了进程隔离的代价，没拿到并行的收益」。

### P3 · 交互与状态层

#### P3-1 文档锁争用
`_document_lock` 在 viewmodel 层出现 **53 处**。历史回归测试已记录过「持锁 1003 ms，主线程拖拽同时被阻塞 980 ms」的事故。

#### P3-2 220 ms 静止延迟
`_final_preview_timer` 固定 220 ms。松手后用户要等 220 ms 才看到清晰画面 —— 这是设计选择，不是 bug，但在大画布上叠加 263 ms 渲染，体感变成「松手后半秒才清晰」。

#### P3-3 QML 侧
`Main.qml` 9,301 行单文件、1 个内联 component 计数（说明组件化未做），属性绑定链深。UI 层本身由 Qt 的 C++ 场景图渲染，**不是瓶颈主因**，但改动风险高、可维护性差。

## 五、现有架构的限制

不是「写得不好」，是几个设计选择在大画布场景下开始反噬。

### 5.1 渲染是「即时模式」而非「保留模式」
每帧从头重建整张画布。Photoshop / Figma / Krita 都是保留模式（持久画布 + 脏矩形 + 图层合成树）。
这是 4000×5000 只有 3.8 fps 的结构性原因，也是**单点改动收益最大**的地方（-90%）。

### 5.2 缓存是「手写的、分散的、口径不一的」
11 个 `OrderedDict` 各自实现淘汰，2 个有字节预算、9 个没有；每个缓存有自己的 key 构造器（`_build_layer_surface_key`、`_build_layer_interactive_surface_key`、`_build_interactive_base_key`、`_build_layer_positions_key`…）。
后果：**失效逻辑难以推理**（改一个属性该清哪几个缓存？），内存不可预测，命中率无法统一观测。

### 5.3 「快」与「对」用不同的合成路径，靠约定维持一致
- 预览：`_fast_composite` → `_standard_composite_logic`（copy+paste）
- 导出：`document_render.py` → `optimize_composite_layer`（alpha_composite）
两条路径的混合模式实现不完全共享，靠测试兜底。这既是性能分叉点，也是「预览≠导出」的历史复燃点。

### 5.4 序列化格式锁死在 Python 生态
`.cmp` 是 **pickle**（`document_serializer.py:65` `pickle.dump`，`trusted_pickle.py` 做来源校验）。
这一条直接决定了跨语言重写的成本量级 —— 见第六节。

### 5.5 单文件巨型 UI
`Main.qml` 9,301 行。任何 UI 重构都要在这一个文件里动刀，冲突率高、review 成本高。

### 5.6 分层是干净的，但边界是「物理」的而非「逻辑」的
`check_architecture.py` 四项全过 —— 没有 `models → qml` 的反向依赖。这是加分项，说明**代码库本身是可维护的**，不是烂摊子。重写的动机不该来自「太乱」，因为不乱。

## 六、重写可行性评估

### 6.1 成本量化

| 迁移对象 | 规模 | 可复用性 | 说明 |
|---|---|---|---|
| QML 界面 | 15,271 行 | **100% 可复用** | Java 可用 QtJambi（社区维护、落后主干），但更现实的是换成 JavaFX —— 等于 15K 行 UI 全重写 |
| Python 业务逻辑 | 68,575 行 | 0% | 文档模型、图层、绑定、预设、导出计划、序列化 |
| 测试 | 1,180 项 | 0% | 全部重写；且这些测试里有大量像素级断言（测真实渲染结果），重写后需要重新建立基线 |
| `.cmp` 文件格式 | pickle | **0%** | Java 无法读 Python pickle。必须先用 Python 写一个「pickle → 中间格式」转换器，且要覆盖所有历史版本兼容分支（`serialization_compat.py`） |
| 预设文件 | pickle | 0% | 同上 |
| 打包/更新链 | PyInstaller + NSIS + update.json | 重做 | JRE 打包（jpackage）体积 ≈ 50 MB 起 |
| **用户已存文件** | 未知数量 | **必须迁移** | 一旦有用户数据，格式迁移是**不可逆的兼容负担** |

### 6.2 收益量化（关键）

假设 Java 重写后业务层开销归零（乐观）：

| 指标 | 现在（Python） | Java 重写（乐观上限） | 换 libvips（推荐） |
|---|---|---|---|
| 8 层 1080×1350 交互帧 | 31 ms | ~20 ms（省掉 35% 业务层） | **~10–15 ms** |
| 4000×5000 8 层 | 263 ms | ~170 ms（仍受 copy 地板限制） | **~25 ms**（脏矩形 + vips） |
| 批量吞吐 | 5.3 张/秒 | ~7–9 张/秒（并发上限提高后，实测 4 线程 1.72×）| **30–60 张/秒**（引用同量级基准） |
| 峰值内存 | 1.3 GB | ~800 MB（BufferedImage 本身开销大） | **~200 MB** |

**结论**：Java 的乐观上限还不如「原语言 + 换库 + 改算法」。因为 Java 的图像基座（`BufferedImage` + `Graphics2D`）本身就是被 libvips 碾压的那一层。

> 引用：单张图片缩放实测 —— `Graphics2D` 22 ms / `Thumbnailator` 23–30 ms / `ImageJ` 120 ms / OpenCV 8 ms / libvips 4.4 ms（同硬件同图）。
> 换到 Java 是从「Pillow 档」挪到「Graphics2D 档」，两者同一量级；跳到 libvips 才是换档。

### 6.3 风险量化

| 风险 | 概率 | 影响 |
|---|---|---|
| 功能回退（边缘功能漏迁） | **高** | 用户投诉、口碑 |
| `.cmp` 历史文件打不开 | **高**（pickle + 多版本兼容） | 致命 |
| 像素级输出差异（混合模式、描边、字距） | **高** | 「预览≠导出」再次复燃，且更难对齐 |
| 工期失控 | 高 | 6–12 个月无新功能 |
| 团队学习曲线 | 中 | Java + JavaFX/QtJambi 双栈 |
| 并行维护期 | 确定 | 迁移期间两套代码，修 bug 修两遍 |

## 七、候选方案横向对比

评分 1–5，5 最优。「迁移成本」分越高表示越便宜。

| 维度 | ① 留 Python + 改算法/换 libvips | ② C++ / Qt（QML 复用） | ③ Java / JavaFX | ④ Rust / Tauri 或 CXX-Qt | ⑤ C# / .NET + Avalonia |
|---|---|---|---|---|---|
| **渲染性能上限** | 4（libvips 接近 C++ 上限） | **5** | 2 | 5 | 3 |
| **图像生态成熟度** | 4（Pillow + libvips + OpenCV） | **5**（libvips/Skia/OpenCV 原生） | 3（Graphics2D 弱，需绑 OpenCV） | 4（image/vips 绑定） | 4（ImageSharp/SkiaSharp） |
| **UI 层复用** | **5**（QML 一行不动） | **5**（QML 一行不动，只换后端） | 1（JavaFX 重写 15K 行） | 2（QML 需 CXX-Qt 桥） | 1（XAML 重写） |
| **开发效率** | **5** | 2 | 3 | 2 | 4 |
| **迁移成本** | **5**（2–4 周） | 1（8–14 个月） | 1（6–12 个月） | 1（8–14 个月） | 2（5–9 个月） |
| **维护难度** | 4（现状已分层干净） | 3 | 3 | 3 | 4 |
| **打包体积** | 3（118 MB onefile） | **5**（无运行时） | 3（JRE 50 MB+） | **5** | 3（.NET 运行时） |
| **冷启动** | 3（1.2 s） | **5**（~200 ms） | 3（JVM 300 ms+，且业务初始化仍需时间） | 5 | 4 |
| **团队/招人** | 4（现有技能栈） | 2（C++ 难招） | 3 | 2 | 3 |
| **加权结论** | **最优** | 备选（仅在需要极限性能时） | **不推荐** | 长远选项 | 不推荐 |

### 为什么不选 Java（针对本项目）

1. **UI 层零复用**。QML 本来就是 C++ 渲染的，Java 接不进来。要么用 QtJambi（社区项目、版本滞后），要么换 JavaFX 重写 15K 行。
2. **图像基座不升反平**。`Graphics2D` 与 Pillow 同档，都输给 libvips 数倍。要追上必须再绑 OpenCV —— 那已经是「JNI + native 库」，Java 的语言优势在这条链路上不存在。
3. **`.cmp` pickle 格式是硬墙**。跨语言无法直读。
4. **收益天花板低于成本**。省 35% 业务开销，代价是 68K 行 + 1,180 测试 + 用户文件迁移 + 6–12 个月。

### 为什么不选 Rust / C++
技术上最正确的方向，但对**当前阶段**是过度投资。C++/Qt 的价值在「无运行时、启动 ~200 ms、可达 libvips 上限」，这些收益可以通过「Python + libvips」拿到 80%，成本差一个数量级。
**保留为阶段三的可选动作**：如果 libvips 之后仍不够（比如要上 GPU 实时滤镜、4K 视频预览），再把渲染内核抽成独立 native 扩展，QML 与业务逻辑不动 —— 这是可渐进的，不是全有或全无。

## 八、推荐方案

**主线：留在 Python + QML，重做渲染内核的三件事 —— 脏矩形、libvips、缓存预算。**

### 阶段 0 · 止血（1–2 周，不改架构）

预期收益：**卡顿场景 60–70% 消失，内存回落 70%**。全部是局部改动，风险可控。

| 动作 | 位置 | 预期 |
|---|---|---|
| 1. 合成改为局部区域（去掉每层全画布 copy） | `unified_alpha_compositor.py:490` | 帧时间 -40%（实测 398→240ms） |
| 2. 交互帧引入脏矩形，只重合成被操作图层的新旧矩形 | `fast_renderer_preview.py` + `workspace_vm_preview.py` | 大画布 -90%，3.8 fps → 30+ fps |
| 3. 持久画布，复用透明底图，不每帧 `Image.new` | `document_render.py:789` | 省 76 MB memset/帧 |
| 4. 给剩余 11 个缓存补字节预算 + 驱逐时 `close()` | `fast_renderer.py:243–310` | 峰值内存 1.3 GB → ~300 MB |
| 5. 提高并发上限（现状 28 核只跑 5 线程，上限偏保守） | `obe_memory_guard.py:267` + `obe_io_export.py:407` | 吞吐 +30~60%（实测 4 线程 1.72×，非 4~6×）|
| 6. 导出进程常驻（复用而非每次重启） | `export_worker_client.py` | 省 1.5 s/次 |

**验收口径**（要写进测试，不能靠体感）：
- 4000×5000 / 8 层拖动 ≥ 30 fps
- 20 次预览后 RSS 增幅 < 200 MB
- `python -m pytest` 全绿，`test_interaction_smoothness.py` 增加脏矩形断言

### 阶段 1 · 换基座（3–4 周）

| 动作 | 说明 |
|---|---|
| 1. 引入 libvips 作为合成/缩放/编码后端 | 项目已有 `vips_export_engine.py` 骨架（当前 pyvips 未安装，自动回退 Pillow），扩展为全链路 |
| 2. 保留 Pillow 作为回退 | 沿用现有「不可用即降级」契约，打包时把 libvips DLL 打进安装包 |
| 3. 合成改为 vips 的 demand-driven 流水线 | 只在 `write_to_file` 时真正执行，内存占用按条带流动，不再整图驻留 |
| 4. 建性能基准测试 | 固定 3 组图（1K/2K/4K）× 层数（1/4/8/12），进 CI，回归即报警 |

**验收口径**：批量吞吐 ≥ 25 张/秒（8 层 1080×1350 PNG）；4000×5000 8 层单帧 < 60 ms。

**这一步的性价比是整个方案里最高的**：换一个库，拿 2–3× 合成速度 + 1/5 内存（引用基准口径）。

### 阶段 2 · 结构收敛（2–3 周，可与阶段 1 并行）

| 动作 | 说明 |
|---|---|
| 1. 统一缓存层 | 11 个 OrderedDict → 1 个带字节预算的 LRU + 明确的 key 规格表；对外只暴露 `get(key, factory)` |
| 2. 预览/导出合成路径合一 | 消除「快路径」与「对路径」的实现分叉，改为同一实现 + 质量参数 |
| 3. 拆分 `Main.qml` | 按抽屉/面板拆成独立组件，先拆无状态面板（低风险） |
| 4. `IntelligentRenderCache` 决策 | 要么接入热路径，要么删除。不要留着「有缓存但 0 命中」的假象 |

### 阶段 3 · 可选 native（仅当触发「改口条件」）

把渲染内核（合成树 + 脏矩形调度）抽成 C++/Rust 扩展，通过 pybind11 / PyO3 暴露给 Python。QML 与业务逻辑不动。**这是渐进替换，不是重写项目。**

---

## 九、改口条件（什么情况下我会推翻上面的结论）

诚实地说，以下三条任意一条成立，我就改推荐：

1. **需要「无 Python 运行时」的交付形态**（比如嵌入第三方宿主、绿色单文件 < 20 MB、或客户合规禁止 Python）。
   此时 C++/Qt + QML 是对的，因为 QML 复用、体积小、启动快。Java 依然不选。

2. **需要实时视频/4K 序列预览、或 GPU 滤镜链**。libvips 不够，需要 Skia/OpenGL 直通。此时 native 内核（阶段 3 提前）是必须的，但仍不必重写业务层。

3. **团队技能栈真的转向 Java 生态**，且未来要做「服务端批量渲染 + 多端协同」。
   在这个前提下 Java 有它的道理（服务端生态强）。但注意：**这时不该重写桌面端，而是新写一个服务端渲染服务**，桌面端继续留着。两者共用 `.cmp` 的 JSON 导出格式即可。这比「重写桌面端」便宜一个数量级，且不牺牲现有用户。

## 十、主要风险与注意事项

### 改算法时的风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **脏矩形算错 → 画面残影/漏画** | 图层旋转、描边、阴影的外扩区域超出图层 bbox | 脏区域必须包含「效果外扩量」（描边宽度、阴影偏移+模糊半径、圆角）|
| **预览与导出结果分叉** | 局部合成与全量合成在边界处理上不一致（半透明边缘、混合模式） | 保留像素级对照测试：同一文档，脏矩形路径与全量路径的输出必须逐像素相等 |
| **混合模式在局部区域失效** | 部分混合模式（如 `overlay`/`soft-light`）依赖上下文，局部裁剪会改变结果 | 这类模式强制走全量路径；只有 `normal` 走脏矩形 |
| **GPU/驱动差异** | 若后续引入 GPU 路径，不同显卡渲染不一致 | 导出固定走 CPU 路径，GPU 只用于预览 |

### 换库（libvips）时的风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **打包体积与 DLL 依赖** | libvips 依赖 glib 等一串 DLL，onefile 模式下解压更慢 | 用 onedir 安装版 + 精简 vips 模块集（去掉 TIFF/PDF/OpenEXR 等未用 loader） |
| **色彩管理差异** | vips 默认带 ICC 处理，Pillow 不带 → 导出色偏 | 显式关闭 ICC 转换，与现有输出对齐后再开 |
| **文本渲染不能用 vips** | vips 的文字能力弱，中文排版（字距、竖排、描边）仍需 Pillow | 文字层继续用 Pillow 渲染成 surface，再交给 vips 合成 —— 分层职责清晰 |
| **首次调用延迟** | vips 初始化有一次性成本（引用：import 173 ms vs Pillow 69 ms） | 启动时预热，或首次导出时预初始化 |
| **降级路径必须可测** | 「vips 不可用自动回退」这条路径平时不跑，坏了不知道 | 加环境变量强制走 Pillow 的测试任务，进 CI |

### 迁移类风险（若最终仍选择重写）

| 风险 | 对策 |
|---|---|
| `.cmp` 无法跨语言读 | 先在 Python 侧提供稳定 JSON 导出（已有 `serialize_document_data` 基础），新实现只读 JSON |
| 预设（pickle）同上 | 同上，且要做批量转换工具 + 用户提示 |
| 像素级输出差异 | 建「黄金图」回归集：20 个典型文档 × 3 种格式，逐像素比对，容差写死 |
| 并行维护期 | 设定明确的切换日与回滚开关，不做「长期双轨」 |

### 顺带该修的（与性能无关但会被上面改动放大）

- `AGENTS.md` 里的「测试 1.5 分钟」已漂移为 **202 s**，建议改为「以 CI 实测为准」而非写死数字。
- `requirements.txt` 缺 `pyvips`（可选依赖未声明），阶段 1 要补 `requirements-dev.txt` 的可选组。

## 十一、一页汇总

| 问题 | 结论 |
|---|---|
| 卡顿主因 | 每层一次全画布 `Image.copy()` + 无脏矩形（占 66% 耗时） |
| 内存主因 | 11 个缓存无字节预算，`_interactive_base_cache` 单点可占 1.2 GB |
| 导出慢 | 并发上限偏保守（28 核 → 5 线程）+ 每次重启子进程（1.5 s 启动税） |
| 是语言问题吗 | **不是**。65% 在 Pillow 的 C 层，Python 业务层仅 35% |
| 该重写成 Java 吗 | **不该**。UI 零复用、图像基座不升反平、pickle 格式硬墙、收益低于成本 |
| 该怎么做 | 脏矩形 + libvips + 缓存预算，分 3 阶段，1–2 周见第一阶段效果 |
| 换语言何时才合理 | 需要无 Python 运行时 / GPU 实时预览 / 团队转 Java 做服务端 —— 且都不是「重写桌面端」 |
