# 批量导出 Manifest 竞争修复设计

## 背景与目标

大批量导出由独立 worker 写入 `.btpw_export_manifest_*.json`，主进程每 0.2 秒读取该文件同步进度。在 Windows 上，主进程持有普通读取句柄时，worker 的 `os.replace()` 可能因目标文件不允许删除共享而抛出 `WinError 5`。异常随后中断导出统计，使自动调优回退误判为“尚未完成任何任务”并从头重试，造成重复写盘；再次启动时，现有代码还会在读取续传状态之前覆盖旧 manifest。

修复目标：

- manifest 短暂被占用时，worker 能在有限时间内完成写入。
- 诊断或进度记录失败不能把已经成功的图片写盘判为失败。
- 再次启动相同导出请求时，先恢复已有完成文件，再发布新的运行状态。
- 自动调优回退只在确实没有成功落盘时重试，避免重复执行同一计划。
- 导出报告中的完成数量与实际成功写盘数量一致。

## 方案比较

### 方案 A：局部加固现有 JSON manifest（采用）

保留现有进程模型和 JSON 协议，在 manifest 原子替换处增加仅针对 Windows 占用错误的有限重试；将进度回调视为非关键观察逻辑；在启动写状态前读取续传数据；持续同步成功计数供外层回退判断。

优点是改动集中、兼容现有打包方式和诊断文件，风险最低。缺点是 JSON 轮询仍有少量 I/O，但不属于本次故障范围。

### 方案 B：主进程改用 Windows 共享删除读取句柄

通过 Win32 API 打开带 `FILE_SHARE_DELETE` 的读取句柄，从源头允许替换。

它能消除特定竞争，但引入平台专用代码，且不能防御杀毒软件、索引器或其他程序短暂占用目标文件，也没有解决续传顺序和回调异常传播问题。

### 方案 C：改用 IPC 或 SQLite 传递进度

以管道、套接字或数据库替代 JSON 文件轮询。

长期架构更清晰，但会扩大打包、进程生命周期和恢复协议的改动面，不符合本次最小修复目标。

## 详细设计

### Manifest 写入

`ManifestWriter._write_locked()` 继续先完整写入临时文件，再原子替换目标。替换遇到 `PermissionError` 或 Windows `winerror == 5` 时进行短间隔、有限次数重试；其他异常立即抛出。每次重试复用已经完整落盘的临时文件，不重新序列化 payload。

超过重试上限后，调用方记录 manifest 写入失败，但图片渲染和写盘流程不因此中断。最终状态写入仍应尽最大努力执行；若始终失败，worker 退出状态可以反映诊断通道异常，但不能触发重复图片任务。

### 回调隔离与真实计数

成功保存图片后，执行器先更新自身 `completed_count`，再调用文件完成和进度回调。两个回调分别捕获异常并记录警告，不把观察层故障转换成渲染/保存失败。

`self.stats["completed_count"]` 在每次成功保存后即时更新，而不是只在整批循环正常结束时更新。自动调优回退继续使用该字段，因此只要已有一张成功落盘，就不会从头重试整个计划。

### 续传顺序

worker 创建 `ManifestWriter` 后，必须先从磁盘读取并校验旧 manifest，再写入 `"loading"` 或 `"running"` 状态。恢复只接受请求关键字段一致且文件仍存在的完成项，沿用现有 `_same_request()` 规则。

恢复成功后，新 payload 保留 `completed_files` 和 `resume_from`，后续只生成剩余数量，并把起始编号向后移动。

### 错误与报告

manifest 写入警告保存到 worker 日志，并尽可能附加到最终报告的额外诊断字段。图片保存错误仍按现有安全阈值处理。最终 `exported_count` 使用真实 `completed_count`；若执行失败，也不再错误显示为 0。

## 测试与成功标准

新增轻量级单元测试，避免启动完整 PySide6 UI：

1. 模拟 `os.replace()` 前两次抛出 WinError 5、第三次成功，断言 manifest 最终可读且替换调用三次。
2. 模拟替换始终失败，断言重试有上限并保留明确错误。
3. 预置含有效完成文件的旧 manifest，调用恢复流程后再发布启动状态，断言完成记录未被清空。
4. 执行最小保存任务并让进度回调抛异常，断言任务仍计为成功，且 `stats["completed_count"]` 已更新。
5. 验证已有成功落盘任务时，不满足自动回退条件。

完成标准是上述回归测试通过，相关 Python 文件可编译，现有测试（若可运行）不新增失败，且 git diff 只包含本次规格、测试和必要实现。
