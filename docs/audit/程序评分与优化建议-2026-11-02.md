## 一、综合评分：**8.3 / 10**

> 评分经过两次调整：
> - 初评 **8.0**（2026-11-02 上午）—— 基于静态与实测数据。
> - 执行后 **8.3**（同日下午）—— 修掉 2 个真实缺陷、补齐日志轮转与工具链，
>   并把 4 条约束固化成可执行检查。

> 上调不是"干完活就加分"，而是原评分低估了两件事：
> ① 缺陷密度比静态扫描显示的更高（两个崩溃级 bug 藏在"未使用变量"和
> "测试 flaky"这两类看似无害的信号后面）；② 约束一旦机器化，后续退化的

## 二、三条最该先动的（按性价比排序）

> **执行状态（2026-11-02 当日完成）**
> 本节 P0 / P2 已修完并提交，另在修复过程中发现并修掉一个真实并发缺陷。
> 详见文末「九、执行记录」。以下保留原始问题描述，便于回溯。

### P0 · 日志系统：1,627 个文件、无轮转、每次启动新建一个

**实测证据**

```
~/.config/批图王/logs/  →  1,627 个 .log，12 MB
最大单文件 2.8 MB（22,918 行）
代码里 RotatingFileHandler / maxBytes / backupCount  →  0 处
app/utils/logger.py:160  log_file = f'app_{timestamp}.log'   ← 每次启动新文件
```

即"打开一次软件 = 多一个文件"，永不清理。用户用两年就是几千个文件。
排查问题时无法按级别过滤，也无法按时间窗口定位。

**同一处的第二个问题：44 处日志标签的中文被吞掉了**

```python
# app/utils/obe_plan_execution.py
print(f"[] : {self.total_tasks} ")        # 原意是 "[批处理] 任务数量: N"
# app/utils/batch_export_generation.py:830
print(f"[V2] : {count} ")                  # 原意是 "[V2] 生成组合数: N"
```

全仓 44 处命中，集中在 7 个文件（`obe_plan_execution` 15、`batch_export_precomputer_v2` 9、
`obe_task_render` 8、`optimized_batch_executor` 5 …）。
**已追溯**：这不是这次改坏的，基线提交 `618cd7f`（v1.1.5）里就是这样 —— 大概率是当年某次
批量正则替换 / 编码转换把中文字符串吃掉了。只影响日志可读性，**不影响任何业务逻辑**（已逐行确认）。

**改法**：`RotatingFileHandler(maxBytes=5MB, backupCount=5)` + 一次性补齐 44 处标签。
成本约 1 小时。这是投入产出比最高的一项 —— 它决定"用户报障时你能不能查"。

### P1 · 可维护性：92 个函数 >80 行，最复杂的一个 724 行 / 148 分支 / 嵌套 10 层

| 函数 | 行数 | 分支 | 嵌套 | 位置 |
|---|---|---|---|---|
| `_generate_binding_combinations_v2` | 724 | **148** | 10 | `utils/batch_export_generation.py:100` |
| `export_batch_optimized_v2` | 514 | 140 | 4 | `utils/optimized_batch_executor.py:158` |
| `qml_main.main` | 668 | 134 | 7 | `qml/qml_main.py:153` |
| `_render_with_combination` | 374 | 117 | 9 | `utils/obe_task_render.py:513` |

参考系：`radon` 默认把圈复杂度 **>10 判为复杂**，McCabe 原始论文建议单函数 ≤10。
这里有 **73 个函数分支 >20**。不是说非要压到 10，而是 148 分支的函数改一行要通读全篇 ——
这也是 10-29 那份审计里"拆 `render_composition` 拆出两个真 bug（NameError 被 except 吞掉）"的同一个成因。

另一个更贵的点：**`Main.qml` 单文件 9,289 行，26 处弹窗/抽屉全部内联**，
其中最后一块（多标签导出抽屉）独占 4,797 行。
改画布交互时会被无关代码干扰 —— 这点你自己在 10-29 审计里已经提过（"前几轮修 bug 时有体感"）。

**改法**：不用一次全拆。`qml_main.main` 拆成 `_parse_args / _build_engine / _bind_viewmodels / _apply_debug_entries`
四段，是纯机械操作且有 825 项测试兜底，风险最低，建议先做这一个当样板。

### P2 · 交付纪律：90 个文件、+2,764 / −7,648 行，5 天没有提交

```
git log -1  →  2026-10-28 22:31  「默认主题改为深色」
git status  →  78 M + 12 D + 30 ??      （未跟踪里还含 6,239 行代码）
```

## 五、做得好的部分（不是客套，是资产负债表）

这几项决定了"能不能继续往上加功能"，值得保住：

1. **预览 = 导出，像素级零差异**。实测 3 图层叠加，平均差 0.0000、最大差 0。
   同类工具（含商业产品）最常翻车的就是这块，这里做到了。
2. **pickle 反序列化上了白名单**。`.cmp` 是 pickle 载荷，本来是 RCE 面；
   项目用 `RestrictedUnpickler` + builtins 纯数据类型白名单 + `app.*` 命名空间收口，
   `os` / `subprocess` / `eval` 一律拒收。这是很成熟的防御，很多同类工具没做。
3. **分层没有反向依赖**。`models`·`utils`·`services` → `qml` 反向引用 0 处；
   112 个模块里只有 1 对双向依赖（`text_layer` ↔ `text_layer_serialize`）。
4. **裸 `except:` 清零**，且 0 处未指定类型的捕获。
5. **批量导出的降级是可解释的**。实测请求 12 张、唯一组合只有 6 个 → 实出 6 张，
   report 里 `planned_count=6 / exported_count=6` 如实记录，UI 侧
   `adjustmentSummary` + `degradationSummary` 双通道提示都已接进 QML。
   这比"悄悄少出 6 张"高一档。

## 六、P3 及之后（可排期，不急）

**更新清单签名**
现状：清单走 GitHub raw → jsDelivr → 5 个第三方 gh 代理回退；SHA-256 在清单里自校验。
问题：清单和哈希同源，能改清单的人也能改哈希，SHA-256 只防传输损坏、不防篡改。
业界做法：Tauri Updater 用 minisign 签名清单、Sparkle 用 EdDSA——
公钥硬编码在客户端，私钥离线保管。改造量约 1 天，收益是把"信任根"从网络挪到本地。

**静态检查落地**
现在 CI 只有 `compileall`，等于只查语法。建议 `ruff`（`F401` 未使用 import、`F841` 未使用变量、
`E501` 行长）+ `import-linter`（把"零反向依赖"这条从口头约定变成 CI 断言）。
参考：ruff 的 `F` 规则集是 Flake8 的超集，性能高一个量级，适合本仓库体量。

**测试补强要挑地方**
不要追覆盖率数字。优先补 `batch_export_precomputer_v2`（1,498 行，覆盖率 47.8%）、
`batch_export_generation`（1,180 行，46.4%）、`binding_group_matching`（41.0%）——
这三个是批量导出的核心，也是当前测试最薄的。做法参考你已有的成功经验：
`probe_render_baseline.py` 的"场景指纹"模式，比逐函数单测更能锁住行为。

**QML 测试的类型失衡**
40 个 `test_qml_*.py` 里，只有 **4 个真正加载 QQmlApplicationEngine**，
**17 个是读 .qml 文本跑正则断言**。后者能锁"某个色值别改回去"，
但锁不住"改完还渲染得出来"。建议关键改动至少配一个真加载的冒烟用例。

### 9.2 修复过程中发现的真实缺陷（不是测试问题）

**现象**：`test_qml_canvas_drag_updates_real_layer_geometry` 全量跑时偶发失败，
报 `resize mismatch: before=(354, 94), after=(788, 248)`。单跑 3 次又全过。

**定位过程**（记下来是因为前两轮判断都是错的）：

1. 先怀疑测试 flaky、时序不稳 → 连跑 10 次量化：**失败 4 次**，而且
   `before` 恒为 `(354, 94)`、`after` 恒为 `(788, 248)` —— **精确 2 倍**，
   不是随机抖动。定量特征立刻否掉了"时序抖动"的假设。
2. 怀疑坐标单位混用（屏幕 px vs 画布单位），算了半天对不上 2 倍。
3. 在 `applySelectedGeometry` / `previewLiveGeometry` 两侧埋点 → **入参完全相同**
   （都是 394×124）。说明问题不在写入，在**读回**。
4. 在 `TextLayer.width` 的 setter 里加栈追踪 → **setter 只被调用一次，值是对的**。
5. 于是查 `_width` 的直接写入点 → 命中 `text_layer_render.py` 的
   `_render_text_supersampled`：它把 `_width` 原地 `*= 2` 做超采样，
   `finally` 再还原。而 `width` getter **不加锁**。

**根因**：`render_text()` 持 `_render_lock`，但 getter/setter 不持。
后台线程渲染期间，主线程读尺寸就会拿到"放大中的临时值"。

**这不只影响测试**：用户在画布上拖动文字图层缩放手柄时，
只要预览渲染恰好落在读尺寸的瞬间，宽高就会被放大 2 倍。
文字图层是这批素材的主力图层类型，触发面比测试里宽得多。

**修复**：`width` / `height` 的 getter 与 setter 都持 `_render_lock`
（与 `render_text` 同一把 `RLock`，可重入，不会自锁）。

**验证**：
- QML 交互探针连续 **25 次全通过**（修复前 15 次挂 2 次）
- 新增 `tests/test_text_layer_concurrent_size.py` 4 项；临时移除 getter 锁后
  立即失败并报 `读到 5899727 次非逻辑尺寸，样本 (708, 188) = 354×2 / 94×2`，
  确认测试能检出该缺陷

本次按上下文与变量语义**重建**，已在提交信息里注明是重建而非还原。
影响：仅诊断输出可读性，不影响导出逻辑与产物。

### 9.4 工具链落地：为什么 import-linter 换成自研检查器

计划里写的是 ruff + import-linter，实际落地是 **ruff + `tools/check_architecture.py`**。
换的理由是实证的，不是偷懒：

- 本机 `pip install ruff` 直接失败：`ProxyError: Tunnel connection failed: 502`。
  当前环境**装不上任何第三方包**。
- 后果：若规则只写在 CI 里，日常开发时它就不存在 —— 提交前无法自查，
  等 CI 变红才知道，反馈环路从"秒级"变成"推送后几分钟"。
- 自研版本纯标准库，**离线可跑**，且能报精确行号；本项目要守的规则只有 4 条，
  引入一个几百行的外部依赖换不来对应收益。
- CI 里仍跑**真 ruff**作为权威判定，两套并存：本地快反馈、CI 做终审。

维护约定（已写进 AGENTS.md 与脚本注释）：改 `ruff.toml` 的 `select`
必须同步 `check_architecture.py`，反之亦然。

### 9.5 本轮新增的第二个真实缺陷：Alpha 兜底路径崩在半路

清 F841（未使用变量）时，`_basic_dark_edge_fix` 报出 `img_array`、`a_smooth`
两个"算了不用"的变量。查上下文发现不是未使用，而是**函数体被劈开了**：

```python

    if background_color:
        import numpy as np
```

两条后果：

1. **传 `background_color` 时该函数返回 `None`**。而它是
   `fix_png_dark_edges` / `auto_fix_png_for_background` 在
   「PNG 优化不可用」或「优化抛异常」时**唯一的兜底**。兜底返回 None，

### 9.6 自己引入又自己修掉的坑：日志清理放启动主路径

第一版把 `prune_legacy_log_files` 同步放在 `Logger.init` 里，**7 项单测全绿**。
实机跑才发现代价：本机 1,578 个历史日志，同步删除耗时 **2 分 25 秒**
（每次删除都走系统回收站）。等于"打开软件先卡两分半"。

修复：改守护线程 + `LEGACY_LOG_MAX_DELETE=200` 单次上限。
`Logger.init` 从 **2m30s → 0.050s**。

**写这条回归测试时断言错了两次**，记下来：

| 版本 | 断言 | 为什么错 |
|---|---|---|
| v1 | `init` 耗时 < 2s | 同步实现因 `max_delete=200` 生效，删得快也能过 |
| v2 | `init` 返回时历史日志还没删完 | 同步删到 200 上限后仍会剩文件，同样能过 |
| v3 ✅ | 清理执行的**线程身份** ≠ MainThread | 唯一能稳定区分同步/异步的判据 |

把实现改回同步后，只有 v3 会报「清理在 MainThread 上同步执行」。

**教训**：单测全绿不代表功能可用。**新增的启动路径逻辑必须实机跑一次**。
以及：断言要挑"两种实现必然不同"的观测量，别挑"顺带不一样"的间接指标。

### 9.7 拆 `qml_main.main`：以及"源码搜索型测试"的坑

`main()` 从 **668 行 / 约 134 分支**降到 **288 行 / 36 分支**，
调试分支搬进新文件 `app/qml/qml_debug_entries.py`。

拆完跑全量测试，**4 项失败**。逐个核对后都不是改坏功能，而是测试写法的问题：

| 失败测试 | 断言内容 | 真实原因 | 处理 |
|---|---|---|---|
| `test_qml_export_and_color_picker_layout` | 源码含 `findChild(QObject, "effectColorDialog")` | 只读 `qml_main.py`，代码搬家 | 改读「启动器全量源码」（两文件合并） |
| `test_qml_theme_switching` | 源码含 `"setThemeMode", Q_ARG(...)` | 同上 | 同上 |
| `test_qml_workspace_chrome` | 源码含 `include_initial_document=initial_document_requested` | 同上，且变量被抽成了函数 | 改读全量源码 + 断言改为等价的 `wants_initial_document(args)` |
| `test_qml_home_routing` | 源码含 `open_presets_as_home` | 同上 | 见下 |

**这里有个更值得记的发现**：`test_qml_home_routing` 原本**自己复刻了一份首页判定逻辑**
（用同名字段重写一遍布尔表达式），而不是调用真实实现。这意味着：
实现把 `or` 改成 `and`，测试照样全绿 —— 它测的是"复刻的副本"，不是产品代码。

本次改成直接调用 `wants_initial_document`，另加一条断言把判定条件与源码字面对齐。
验证方式：把源码里的 `or` 手动改成 `and`，该断言立刻报
「open_preset_workbench 的首页判定条件被改动了」。改回后恢复通过。

**通用教训**：
- 「源码里必须包含某字符串」型测试，一旦代码搬家就会批量误报。要么读"能力所属的全体文件"，
  要么直接调用真实函数 —— 后者永远优于"复刻一份逻辑再测复刻"。
- 复刻型测试是**假保险**：它不会因为你改坏实现而失败，只会在你改坏那份复刻时失败。

**过程中我自己踩的坑**（记下来避免重犯）：
中途用 `git checkout` 恢复文件时，把同一次会话里已经写入的新函数一起还原了，
导致只剩调用没有定义。以及用字符串切片替换代码块时算错了偏移，产生重复行。
最终改用**按行号定位 + 每步 AST 语法校验**，才稳定下来。
