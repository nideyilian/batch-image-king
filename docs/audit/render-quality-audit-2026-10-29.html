1.1 先清一个坑：有 1000 行描边代码永远不会执行

项目里存在两套描边实现，一套在 layer_effects.py + layer_rendering_mixin.py（约 1000 行，含"现代样式渲染器"、增强圆角、终极圆角三级降级），另一套在 utils/vector_layer_effects.py。

分流开关是 _use_rectangle_vector_pipeline()：

# app/models/layer_vector_mixin.py:148
def _use_rectangle_vector_pipeline(self, stroke_on):
    if self.shape_type != ShapeType.RECTANGLE:
        return True                       # 非矩形 → 矢量管线
    return bool(self.vector_path_enabled or stroke_on or self.corner_radius > 0
                or ...)                   # 有描边/有圆角 → 矢量管线

而调用处：

# app/models/layer_rendering_mixin.py:171-194
if use_vector_pipeline:
    ...apply_vector_path_effects(...)
elif stroke_enabled:                      ← stroke_enabled 时 use_vector_pipeline 必为 True
    if self.stroke_type == 0: self._apply_inner_stroke(...)   ← 永不执行

结论：只要开描边，就一定走矢量管线；_apply_inner_stroke / _apply_center_stroke / _apply_outer_stroke 三个函数、以及整套 enhanced_corner_renderer.py 都是死代码。维护时若去改它们，改动不会出现在任何一张图上。这一条必须先确认，否则后面所有优化都会打偏。

优化方案 A：改用有符号距离场（SDF）描边

一次距离变换同时解决"内外不分"、"圆弧不等宽"、"锯齿"三件事，且天然抗锯齿：

import cv2, numpy as np

# base: 形状填充蒙版 uint8 0/255（已有）
dist_in  = cv2.distanceTransform(base, cv2.DIST_L2, 5)      # 到边界的欧氏距离
dist_out = cv2.distanceTransform(255 - base, cv2.DIST_L2, 5)
sdf = dist_in - dist_out                                     # 正=内部，负=外部，单位 px

# 三种模式统一定义，宽度绝对相等
inner  = np.clip((sdf + 0) / w, 0, 1) * np.clip((w - sdf) / 1, 0, 1)   # 0 <= sdf <= w
outer  = np.clip((-sdf) / w, 0, 1)                                     # -w <= sdf <= 0
center = np.abs(sdf) <= w / 2

关键收益：不再需要沿折线画粗线，圆角与直边的宽度由距离场保证完全一致；边缘是连续值，抗锯齿不依赖超采样倍数。这也顺带解决了 1.2 的位置错误（SDF 的符号本身就区分了内外）。

成本：80~120 行改动，集中在 vector_layer_effects.py
风险：低。SDF 与现有 mask 产物格式一致，可保留旧实现做 A/B 开关
性能：2000×2000 单次 distanceTransform ≈ 8~15ms，比当前 10× 超采样（381MB 分配）更快更省内存

优化方案 B（不想引入 SDF 时的最小修补）

如果只想先止血、不重写几何：

  1. 画 outline 时把宽度改成 stroke_w * 2，这样内外各 stroke_w，再分别按内外裁剪。内/外/居中立刻正确，圆弧宽度也随之对称。
  2. stroke_join 补 bevel 分支（draw.line(..., joint="curve") vs draw.polygon），或明确从 UI 移除这个选项——不要留一个无效设置。
  3. 修 outside_expand：外描边需要 stroke_w 的单边外扩（现在有了，但因为 1.2 全都白扩）。
成本：约 20 行；风险：极低；收益：三个描边模式立刻可用，但圆弧仍偏离 ±20%，做不到"精确"

二、圆角锯齿：锯齿不在你以为的地方

2.1 我原以为的问题，实测不成立

最初怀疑圆角弧段离散化不够（build_rounded_rect_outline_points 固定 24 段）。复算后这个怀疑被否定，如实说明：

圆角半径每段圆心角弦长弦高误差判定
8 px3.75°0.52 px0.004 px无问题
80 px3.75°5.24 px0.043 px无问题
400 px3.75°26.2 px0.214 px肉眼不可见

90° 圆弧用 24 段，每段只有 3.75°，误差远低于 1px。渲染成图放大 4 倍与 32× 超采样对比，边缘平滑度无可辨差异（半透明过渡像素 777 vs 792，边界半径偏差同量级）。10× BOX 降采样对填充边缘是够用的。

2.2 真正的锯齿来源（按可能性排序）

来源位置为什么产生锯齿优先级
预览图缩放 Main.qml:5706-5714 预览 Image 既没设 sourceSize 又 cache:false：全尺寸纹理（4000×4000 ≈ 64MB 显存）缩到窗口大小显示，Qt 线性采样无 mipmap，缩小比例大时圆弧出现阶梯。这是"看画布有锯齿"的最可能原因 P0
圆角描边 vector_layer_effects.py:246 沿折线画粗线，圆弧接头处灰阶突变。叠在圆角外侧，视觉上就是"圆角毛边"（实测宽度偏差 ±22%） P0
二次量化 vector_layer_effects.py:347 putalpha(ImageChops.multiply(...)) 把 float 抗锯齿结果落成 uint8 再乘一次，边缘灰阶被量化两遍，损失约 1 级精度 P2
大图降级 vector_layer_effects.py:14-18 超采样固定 10× 起：2000×2000 图层 = 381MB 单通道，3000×3000 = 1.45GB。到不了这个内存时进程会被系统挤压或直接失败，失败后没有 fallback 到低倍率 P1

优化方案

  1. 预览链路（收益最大、改动最小）：给预览 Image 设 sourceSize: Qt.size(width*dpr, height*dpr)，让解码端直接出目标尺寸；cache 打开并靠 URL revision 控制失效。仅此一项就能消掉缩放假锯齿。
  2. 超采样自适应：把固定 10× 改成按输出尺寸封顶——scale = clamp(2048 // max(w,h), 2, 10)，保证中间蒙版不超过 ~2048²，内存从 381MB 降到 16MB 量级，仍保留足够灰阶。
  3. 消掉二次量化：SDF 方案下全程 float32，最后一次性落 uint8，不做 multiply 链。
成本：预览 3 行 + 超采样 5 行；风险：低；收益：大图不再爆内存、预览锯齿消失

三、尺寸匹配：卡顿的真实成因

先说好的部分：孔位检测主路径用了 cv2.findContours，实测 2000×2000 带 144 个孔 = 19.3ms，算法本身没问题。卡顿来自三处外围开销。

3.1 随机取图时，整份匹配缓存被主动跳过

# app/utils/fast_renderer_surface.py:648-664
session_key = (id(document), tuple(session_parts), relations_hash, was_just_loaded)
if not has_random_source:          ← 只要随机取图，整个会话缓存不查也不用
    with self._size_match_override_session_lock:
        _cached = self._size_match_override_session_cache.get(session_key)
        if _cached is not None:
            return dict(_cached)

批量导出时随机取图是常态而非例外，等于这个缓存形同虚设：每张图都要把所有匹配关系（孔位 → 目标图层位置/尺寸/旋转）从头算一遍。

但随机只影响源图层的像素内容，而孔位是几何属性。真正该做的不是放弃缓存，而是把随机参数纳入 key：

优化方案

# 方案：区分「几何缓存」与「内容」
# 1) 孔位只依赖 alpha 形状 → 按 (源图层, 遮罩参数) 缓存，与随机取图无关
holes = self._get_inner_holes_cached(source_layer, document, was_just_loaded, relation)
# 这是已有缓存，问题在于上游因 has_random_source 整段跳过，根本没走到它

# 2) override 的 key 里带上随机种子，而不是无条件放弃
if has_random_source:
    session_key = session_key + (self._current_random_seed(document),)
成本：约 15 行；风险：中（要确认随机种子在同一次导出内稳定）；收益：批量导出时匹配阶段开销可降一个数量级

3.2 素材池全量 stat 被按"每尝试每层"调用

# app/utils/batch_export_precomputer_v2.py:528
any(... os.path.isfile(path) ... for path in 整个素材池)

实测：3000 个文件全量 isfile = 288ms。被 batch_export_generation.py 的 471 / 748 / 1052 / 1136 四处按"每尝试每层"调用。5000 次尝试 × 5 层 = 25000 次全量扫描。这是数量级错误，不是优化项。

优化方案

素材池是只读的，扫描一次建 set 常驻即可；文件增删由目录监听或导出开始时一次刷新兜住。

self._pool_files: set[str] = {p for p in pool if os.path.isfile(p)}   # 每个池一次
# 之后一律 self._pool_files 成员判断，O(1)
成本：约 10 行；风险：低（需在导出开始/换目录时失效）；收益：单此一项可省数十秒到数分钟

3.3 孔位 fallback 是纯 Python 逐像素 BFS

fast_renderer_surface.py:1209-1399 的 _detect_inner_holes_fallback 用 deque 逐像素四连通 BFS，2000×2000 图要 push/pop 数百万个 tuple。虽然只在 cv2 抛异常时走，但它是静默兜底：一旦触发，单张就要数秒。

用 cv2.connectedComponentsWithStats 一次替代（C 实现），或 scipy.ndimage.label。既然已有 cv2 依赖，这个 fallback 没有理由存在。

成本：约 30 行；风险：低；收益：兜底路径从"数秒"到"20ms"

四、你没发现的问题 · 高优先级

P0 整画布 float32 合成，单层单帧 196MB

app/utils/fast_renderer_composite.py:665-666, 713, 719

为贴一个小图层，把整张画布转 float32：np.array(...)/255 → bg.copy() → 全画布抖动 → 转回 uint8。4800×3200 RGBA 一次 ≈ 196MB/层/帧，且预览模式下只要图层含半透明像素就走这条路（:558-559）。

方案：只对图层 bbox 区域做 float 运算；或全程 uint8 + Image.alpha_composite（已高度优化，无 numpy 往返）。成本：40 行；风险：中（抖动逻辑要保留）；收益：合成阶段内存降 2 个数量级。

P0 撤销重做：每次属性变更全文档 deepcopy

workspace_vm_edit_ops.py:249-273 → document.py:254-270

save_state() = serialize_layer_tree + 3 次 deepcopy 的整文档快照，挂在每一个属性 setter 上。只有不透明度做了合并（workspace_vm_effects.py:416-481），setSelectedStrokeWidth、setSelectedTextBoxPadding 等几十个连续可调值全是逐次全量快照。

拖一次描边宽度滑块 = 几十次整文档快照。这是"拖参数卡"的主因。

方案：把已有的"连续值合并"提炼成 @coalesce("stroke_width", 300ms) 装饰器，覆盖所有滑块型 setter；或改为增量 command（只记 diff）。成本：60 行 + 逐个 setter 标注；风险：低；收益：拖参数流畅度显著提升。

P0 预览渲染：force 是死参数，没有脏检查

workspace_vm_preview.py:24-25：del force 直接丢弃。全工程 33 处 requestPreview(force=True) 与普通调用完全等价。同时 _start_preview_render（:86-118）不比较"上次渲染时文档是否已变"，_render_pending（:144-146）会对同一状态重复渲染。

方案：_last_render_key 记录（文档版本号 + 视口 + 缩放），未变直接返回；force 真正参与判断。成本：25 行；风险：低；收益：消除无意义重渲染。

P0 预览缓存被脏键污染：改文字颜色命中旧图

app/utils/intelligent_render_cache.py:280-296

预览缓存键只含文本 hash、字体、字号、对齐、行距、字距、边距，缺 text_color、text_color_ranges、font_size_ranges、渐变、背景、阴影、发光。改文字颜色后仍命中旧图，用户会看到"改了没反应"。

同类问题：render_cache_keys.py:16-31 分身位置键缺 clone_rows/columns/spacing，改分身行列后位置永远取旧值。

方案：缓存键改为"渲染参数对象的结构化 hash"（对参与渲染的全部字段做一次 tuple → hash），而不是手写字段清单——手写清单必然会漏。成本：50 行，但能一次性杜绝这类 bug；风险：低；收益：消除"改了没反应"类投诉。

P0 图层属性 getter 每次 O(n) 重建显示列表

workspace_vm_view.py:276 → layer_list_model.py:189/200/56-61

几乎每个 @Property（selectedX/Y/Width/Height...）都调 _selected_layer()，而它走 layer_at() → rowCount() → _display_entries()（重建 group_map + 遍历全部图层）。读一个数字 = 一次全量扫描。

data()（:67）每次取一个 role 都重建一次；delegate 声明了 13 个 role，等于每行 13 次构建，100 图层滚动一次 = 上万次。

方案：_display_entries() 结果缓存，仅结构变更时失效；_selected_layer() 直接 document.layers[idx]。成本：30 行；风险：低；收益：面板滚动/选中响应数量级提升。

P0 两处 safe_print 无限递归

app/utils/image_quality_fixer.py:10-21 和 app/utils/enhanced_corner_renderer.py:11-22

def safe_print(message):
    try:
        safe_print(message)      ← 调用自己
    except (UnicodeEncodeError, OSError):
        safe_print(...)           ← 再次调用自己

本意是"编码失败时降级"，实际是无限递归 → RecursionError，把原始异常也吞掉。而这两个模块都在渲染热路径上。

方案：改成 print(message.encode('ascii','ignore').decode()) 或直接用项目的 print_utils.safe_print。成本：4 行；风险：无。

P0 批量导出：每层每任务重复解码图片，结果白做

app/utils/obe_task_render.py:686-694

每层每任务手工调 layer._load_and_process_image(image_path)（磁盘解码 + 缩放 + 2 次全图 copy），结果只写进 _cached_image；而渲染器 fast_renderer_composite.py:200-213 的缓存检查已整段注释，实际走 preload + _process_image。这份预处理 100% 白做。

方案：删掉obe_task_render.py 的手工预处理，或把 fast_renderer_composite.py:200-213 的缓存检查恢复并接上。成本：20 行；风险：中（要确认两条加载路径的产物等价）；收益：导出总耗时里最难 profile 的一块。

P0 随机种子用内建 hash()，跨进程不可复现

batch_export_generation.py:541、batch_export_combination_metadata.py:38

Python 字符串 hash() 受 PYTHONHASHSEED 随机化，注释宣称的"完全确定性、可复现"不成立：同一模板两次导出结果不同，多进程之间也不同。对"批量出图要可复现"是致命伤。

方案：改 hashlib.md5(key.encode()).digest() 取前 8 字节转 int。成本：6 行；风险：低（但会改变已有随机序列，需告知）；收益：真正可复现。

八、什么条件下我改口

上面的结论里，有两条是我用间接证据推的，如果你手上的实际现象对不上，请按下面条件推翻我：

  1. "圆角锯齿主要来自预览缩放" —— 如果在画布 100% 缩放下（actualScale == 1）截图，圆角边缘仍有肉眼可见阶梯，那我的归因错了，问题在渲染器而非预览链路。这时应优先查 _bleed_transparent_edges 与最终合成路径。验证方法：同一图层分别在 100% 和 30% 下截图对比。
  2. "三个描边模式只有两个结果" —— 如果你在 UI 上用外描边确实看到了描边，说明还有一条我没找到的渲染路径（可能走了阴影/发光或位图描边分支）。请告诉我具体是哪种图层（图片层 / 形状层 / 文字层）和外描边宽度，我重新追那条路径。
