二、问题清单（按严重度）

P0撤销历史被浪费一半，约 10 次图层操作就挤掉早期编辑

证据：12 个图层操作函数各自保存两次快照——操作前一次、操作后一次。而撤销只需要"操作前"那一条。

app/models/document_layers.py:34 self.save_state('添加图层前') ← 有用 app/models/document_layers.py:78 self.save_state('添加图层') ← 冗余 同类 12 处： document_layers.py add_layer / add_shaped_layer / add_text_layer / add_existing_layer / remove_layer / move_layer_up / move_layer_down / move_layer layer_controller.py batch_update_layers / delete_layer / _move_layer / paste_layer

实测影响：

max_history = 20 加 3 个图层后: 历史 9/20 加 6 个图层后: 历史 15/20 加 9 个图层后: 历史 20/20 已满 → 之后每次图层操作都会把更早的编辑挤出撤销栈

修法：删掉每条"操作前"或"操作后"中的一条，`max_history` 保持不变即可让可撤销操作数翻倍。约 12 行改动。

风险：低。需注意 `batch_update_layers` 这类批量操作要保证一次批量只留 1 条。

P1add_layer 不校验尺寸，负宽高直接流入下游

证据：构造负尺寸图层时无任何拦截。

d.add_layer("L", 0, 0, -50, -50, is_folder=False) → 接受，w=-50 连锁结果： selectionBoundsX/Y/W/H = 100, 100, -50, -50 ← 负宽高进入 QML 选中框 hitTestLayerAt(110,110) = -1 ← 点不中也选不中 渲染不崩，但图层静默消失（用户以为图层丢了）

修法：在 add_layer 与 Layer.__init__ 把宽高钳到 ≥1，并在选中边界计算里过滤非正尺寸。

风险：低。但要确认没有依赖"负尺寸表示翻转"的既有逻辑——查过，没有。

P10×0 画布被接受，直到导出才报错

d.create_new(0, 0) → 成功，canvase=0x0 后续渲染返回 (0,0) 图像，导出时才报「画布尺寸无效」 对比：export_image 有防护，create_new 没有 —— 校验放错了层

修法：把画布尺寸下限（16×16，与你现有 resizeCanvas 的 16~32768 保持一致）提到 create_new。

风险：极低。resizeCanvas 已经在用 16~32768，口径统一即可。

四、关于那次「冷启动 145ms」的澄清

测到"第一个图层加入耗时 115~145ms"，一开始以为是性能缺陷。cProfile 定位后确认是一次性模块导入：

add_layer 0.145 s └ _invalidate_render_cache 0.139 s └ fast_renderer.py 首次导入 0.136 s └ fast_renderer_surface 0.095 s 第二个图层起：0.35 ~ 0.60 ms

结论：不是缺陷。这是懒加载的正常代价。真要优化，可以挪到启动时预加载（用后台线程），但这只是把 145ms 从"第一次加图层"挪到"启动阶段"，总成本不变。
